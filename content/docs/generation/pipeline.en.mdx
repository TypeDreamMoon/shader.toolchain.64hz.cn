---
title: The Pipeline
description: How one DreamShaderLang source file becomes Unreal assets — every stage, what triggers a build, and where each stage can fail.
---

DreamShaderLang does not compile to bytecode or to an executable. It compiles to **Unreal assets**:
a `UMaterial` or a `UDreamShaderMaterialInstance`, and any number of material-function assets. This
page follows one source file all the way through.

| Aspect | Value |
| :-- | :-- |
| Input | one `.dsm` or `.dsf` file, plus every `.dsh` it imports; the same pipeline compiles `.dss`, `.dsi` and `.dsp` <Since v="2.0.0" /> |
| Rejected input | `.dsh` — a header is compiled only as part of a file that imports it (`DSH8296`) |
| Produces | `UMaterial` / `UDreamShaderMaterialInstance`, `UMaterialFunction`, `UMaterialFunctionMaterialLayer`, `UMaterialFunctionMaterialLayerBlend`. No `.ush` include <Since v="2.0.0" /> — see [The HLSL of a Function](#the-hlsl-of-a-function) below |
| Runs in | the editor process only — the emitter uses editor-only material APIs |

There is no runtime path. Nothing builds a material from DreamShaderLang in a packaged game; by then
the assets already exist.

## Stages

<Since v="2.0.0" /> A `.dsm` / `.dsf` is read by the **legacy front end** into the same tree the `.dss`
parser builds, and from there takes the one pipeline every source kind takes. A stage reports **every**
error it finds; a stage that reported one stops the run before the next stage. Every diagnostic has a
stable `DSHnnnn` code and is reported as `<file>(<line>,<col>): DSHnnnn: <message>` — see
[Diagnostics](/en/docs/diagnostics).

<Wide>

| # | Stage | What it does | Fails with |
| :-- | :-- | :-- | :-- |
| 1 | Normalize path | full path, normalized | — |
| 2 | File-kind gate | builds `.dss`, `.dsi`, `.dsp`, `.dsm` and `.dsf`; a `.dsh` never on its own | `DSH8296` |
| 3 | Read | the file's text | `DSH8290` |
| 4 | Preprocess | [`#if` / `#define`](/en/docs/language/lexical#preprocessor) against the project's define table <Since v="1.9.0" />, in the 1.x dialect for `.dsm` / `.dsf`; directive lines become empty lines, so positions do not move | `DSH8291`, carrying the preprocessor's own `DSH1030`–`DSH1042` |
| 5 | Parse | the legacy front end reads the 1.x blocks, sections and `Graph` statements | `DSH2200`–`DSH2258`, `DSH3250`–`DSH3278`, `DSH5250`–`DSH5265`, `DSH6300`–`DSH6319`, and the lexer's `DSH2101`–`DSH2106` |
| 6 | Bind | names, types, calls, settings; each imported `.dsh` is resolved, preprocessed and parsed **on its own**, and its declarations are declared into the file | `DSH4200`–`DSH4264`, `DSH5200`–`DSH5231`, the legacy rules `DSH5275`–`DSH5292`, `DSH6200`–`DSH6211`, `DSH7200`–`DSH7233`; an import that cannot be resolved, read or parsed, `DSH8292`–`DSH8295` |
| 7 | Build key | hash of every imported header and of the file, plus the settings and versions that decide the output | — see [Regeneration](/en/docs/generation/regeneration#the-build-key) |
| 8 | Lower | the bound tree into the graph IR, Custom-node code included | `DSH4350`–`DSH4383`, `DSH6220`–`DSH6223`, `DSH6250`–`DSH6264`, `DSH6327`, `DSH6328` |
| 9 | Passes, validate | constant folding, de-duplication, dead-node pruning; the IR validator | `DSH4390`; `DSH4300`–`DSH4335` |
| 10 | Emit | one asset per product, in dependency order — see [below](#inside-the-emit) | `DSH8200`–`DSH8237`; two exported functions that call each other, `DSH8299` |
| 11 | Compose result | one line per product, plus a `Warnings:` block — see [Success messages](#success-messages) | — |

</Wide>

A `.dsi` resolves its parent after the parse, and a `.dsp` the materials and shader files its passes
name; see [Material instances (.dsi)](/en/docs/language-v2/instances) and
[Custom Pass (.dsp)](/en/docs/language-v2/passes).

A compile that fails returns the **first error** as its first line, then every other diagnostic of the
run: errors, then warnings, then infos. The result's code is the first error's.

The editor's *compile material* entry point runs the same compile as *compile assets*
<Since v="2.0.0" />: a source is one compile unit, and its material may call a function the same file
declares, which is emitted first.

### Inside the emit

One product — a `Shader`, `ShaderFunction`, `ShaderLayer` or `ShaderLayerBlend` block — in this order.
The diagnostics of the asset layer reach the result inside the emitter's: the emitter's message quotes
the asset layer's code and text.

| # | Sub-stage | Fails with |
| :-- | :-- | :-- |
| 1 | Resolve the destination from `Name=` / `Root=` | `DSH8200` — see [Asset Paths](/en/docs/generation/asset-paths) |
| 2 | Create or reuse the asset: the class check and the [ownership guard](/en/docs/generation/regeneration#the-ownership-guard) | `DSH8201` (`Graph` material), `DSH8203` (ThinCustom instance), `DSH8202` (function, layer, blend) |
| 3 | Another editor owns writing this project's generated assets | `DSH8209`, an info: skipped, not failed |
| 4 | Source-hash short circuit | `DSH8237`, an info: skipped — see [Regeneration](/en/docs/generation/regeneration#when-regeneration-is-skipped) |
| 5 | Open in an asset editor | `DSH8206` |
| 6 | Divergence | `DSH8207` — see [Divergence](/en/docs/generation/regeneration#divergence) |
| 7 | ThinCustom: capture the instance's parameter overrides, then find or create the hidden base | `DSH8230` |
| 8 | Build the graph, apply settings, lay out, recompile — atomically | see below and [Regeneration](/en/docs/generation/regeneration) |
| 9 | Stamp the provenance metadata and the output digest | — |
| 10 | Save, unless the product is an Ephemeral ThinCustom one or writing is refused | `DSH8229` |

The checks the 1.x generator made here — a top-level `Shader` present, a non-empty `Outputs`, a known
`Backend` — are the front end's now: a `Shader` without `Outputs` is the **warning** `DSH2256` and still
builds, a `Shader` with no `Graph` whose `Outputs` compute nothing either is `DSH2255`, and a `Backend`
that is no backend is `DSH7202` (an empty one `DSH7201`; `Instance` is read as `ThinCustom` with
`DSH7204`).

### Inside the graph build

Shared by both backends. For the ThinCustom backend it runs against the hidden base material, not
the emitted instance.

1. Clear the generated `DreamShader: ` comment boxes, then **detach** the existing graph — kept, so a
   failure puts it back (`DSH8208` warns when it cannot be snapshotted).
2. Reset every material property to its engine default.
3. Apply `Settings` (`DSH8215` for a setting the material refuses).
4. Emit the IR graph node by node — parameters, expressions, one Custom node per `Function` call, a
   `MaterialFunctionCall` per `ShaderFunction` call — and connect each `Outputs` binding through a
   `DS_<output>` named-reroute pair. A node the engine could not build is `DSH8210`–`DSH8228`.
5. Lay the graph out in the project's **Graph Layout Style** — on every build <Since v="2.0.0" />; see
   [Layout and #Region](/en/docs/language/layout).
6. Commit — the detached graph is destroyed only now — and recompile the material.

Step 1 is why hand-editing a generated asset is pointless — see
[Regeneration](/en/docs/generation/regeneration).

## What triggers a build

| Trigger | Forced | ThinCustom result | Scope |
| :-- | :-- | :-- | :-- |
| Auto-compile on save — file watcher plus debounce | no | Ephemeral | the saved file; a saved `.dsh` queues every source that imports it |
| The startup sweep, and the sweep after a change to a setting the [build key](/en/docs/generation/regeneration#the-build-key) covers | no | Ephemeral | every project source |
| *Recompile DSM*, *Clean Generated Shaders* | yes | Ephemeral | every project source |
| Material Content Browser *Compile* / thumbnail-refresh buttons | yes | Ephemeral | one source |
| Live preview renderer | through the bridge, yes; through the preview WebSocket, only when the request sets `force` | Ephemeral | one source |
| *Materialize*, and creating a child instance of an Ephemeral material | yes | **Materialized** | one source |
| A `.dsi` whose parent material is missing or older than its source (`DSH8264`) | no | **Materialized** | the parent's source, first |
| Commandlet `-run=DreamShader` | with `-Force` | **Materialized** | as asked |
| Cook, on the cook director process only | yes | **Materialized** | every project source |

Auto-compile is governed by two project settings: **Auto Compile On Save** (default on) and **Save
Debounce Seconds** (default `0.25`, clamped to `[0.05, 10.0]`). With the first one off, the source
watcher ignores changes entirely. See [Project Settings](/en/docs/settings/project).

<Callout type="info">
**Only a ThinCustom product can live in memory.** The interactive editor keeps it Ephemeral until a
cook, the commandlet or an explicit *Materialize* puts it on disk. A `Graph`-backend material and every
material function, layer and blend are saved by every build that is allowed to write
<Since v="2.0.0" />. See [In-memory Materials](/en/docs/generation/in-memory).
</Callout>

<Callout type="info">
**A batch compiles in dependency order** <Since v="1.8.0" />. A material that calls a `ShaderFunction`
binds its call node against the **live** `UMaterialFunction` asset — the emitter reads the pins off the
object, not off the source — so compiling the caller first binds it against the *previous* version of
that function's interface. When a batch holds both a file and something it depends on (a header it
imports, the parent of a `.dsi`, a material a `.dsp` names), the dependency compiles first; inside one
file a function another product calls is built first too, and two exported functions that call each
other are `DSH8299`. Files in an import cycle stay in the order the walk reached them; the compile
rejects the cycle with `DSH4211`. `compile -All` and the cook also **retry in passes**
<Since v="2.1.2" /> — see [Commandlet](/en/docs/tools/commandlet#-all-discovery-and-ordering).
</Callout>

## Outcomes that are not assets

A source file can compile successfully and produce nothing to place in the Content Browser.

| Source | Outcome |
| :-- | :-- |
| a `.dsm` / `.dsf` that declares only `Function`, `GraphFunction`, `Namespace` or `VirtualFunction` blocks | **success**: `Compiled {File}; it declares no material and no exported function, so no asset was written.` |
| a `.dsm` / `.dsf` with no block at all | **failure**, `DSH2254` |

## Success messages

One line per product, in the order the products were emitted. The lines are a wire format: a script
reads `Generated <Kind> <ObjectPath> from <Source>.` to list what a run wrote.

| Message | Emitted for |
| :-- | :-- |
| `Generated {Kind} {ObjectPath} from {File}.` | each product built. `{Kind}` is `Material` (either backend), `MaterialFunction`, `MaterialLayer`, `MaterialLayerBlend`, `MaterialInstance` or `PassPipeline`; `{ObjectPath}` is the object path, `/Game/M.M` |
| `Generated RenderTarget {ObjectPath} from {File}.` | the render target of each exported buffer of a `.dsp` <Since v="2.1.0" /> |
| `Skipped {ObjectPath} from {File}; source hash is unchanged (build key {BuildKey}).` | a product the hash short circuit skipped, of any kind |
| `Skipped {ObjectPath}; another editor owns this project's DreamShader bridge, and only that one writes generated assets to disk.` | a product another editor owns the writing of (`DSH8209`) |
| `Compiled {File}; it declares no material and no exported function, so no asset was written.` | a source with no product |

`{File}` is the full, normalized source path. Under the lines, a `Warnings:` header lists every warning
of the run in wire form, then the generation warnings `DSH8155`, `DSH9011` and `DSH9012`. Warnings
never fail a compile.

<Callout type="info">
<Since v="2.0.0" /> The 1.x lines `Generated {AssetPath} from {File}.`, `Generated DreamShader
thin-custom material …`, the ` (virtual)` suffix and the helper-include line are gone: every product
says `Generated` with its kind, and a function skipped by the hash says `Skipped` instead of nothing.
</Callout>

`{Placeholder}` on this page marks a value the compiler substitutes at run time.

## Progress reporting

Generation reports through Unreal's slow-task system. The dialog is delayed so a fast compile never
flashes one, carries a **Cancel** button <Since v="1.9.0" />, and is not shown at all under
`IsRunningCommandlet()`.

| Scope | Title | Frames | Dialog delay |
| :-- | :-- | :-- | :-- |
| one compile | `Compiling DreamShader source '{File}'...` | 6: `Reading`, `Parsing`, `Resolving names in`, `Lowering … to IR`, `Validating the IR of`, `Building the graph for '{File}'...` | 0.35 s |
| `Classic` layout (nested) | `Laying out DreamShader material graph...` | one per node | inherited |

The first five frames are the front end, and quick. The last, `Building the graph for …`, holds the
emit — and the emit ends in the shader compile, which is unbounded. A bar that stops on that frame is
normal: shader compilation happens outside the plugin, and one heavy permutation can hold it for minutes.

### Cancelling

<Since v="1.9.0" />

The cancel is checked before every stage, before every product, and inside the emit once the old graph
has been detached. Cancelling takes the same path a failed compile takes:

- The asset is restored to exactly what it held before the compile started — the atomic-rebuild
  rollback does it, so there is never a half-built graph or an emptied material function.
- Nothing is stamped and nothing is saved.
- The compile reports the error `DSH8298` (through 1.x `DSH9010`).

The one thing a cancel does not put back is the generated `DreamShader: ` comment boxes, for the same
reason a failed rebuild does not: they are deleted before the snapshot. The next successful compile
recreates them.

<Callout type="warn">
Cancelling does not stop shaders that Unreal has already queued. Cancel during the shader compile and
`ShaderCompileWorker.exe` keeps working through whatever was already dispatched.
</Callout>

### When a shader compile takes too long

<Since v="1.9.0" />

If the shader compile of one asset runs past **30 seconds**, generation emits `DSH9011` once, as a
warning in the log and in the result's `Warnings:` block. It never blocks or fails the compile; it says
what that wait usually is: a `Custom` node whose loop bound is one of its **input pins** (a `for` or
`while` whose limit is not a literal or a `#define`d constant), combined with **implicit-mip** sampling
(`Texture2DSample`, `Texture3DSample`, `.Sample`) inside divergent flow — the compiler cannot know the
iteration count and fully unrolls the loop. A busy `ShaderCompileWorker.exe` in Task Manager means it
is still compiling, not hung. To fix it, bound the loop with a literal or a `#define`, or call
`SampleLevel` / `SampleGrad`.

Generation also looks for that pair while it emits a `Custom` node's code and warns up front, before
the compile has started, as `DSH9012`. Both are advisory.

## The HLSL of a Function

<Since v="2.0.0" /> A `Function`'s HLSL is written into **the Custom node each call makes**: the node's
`Code` carries the called function's body, verbatim, and every `Function` that body calls, embedded in a
wrapper struct; the `#include` lines at the start of a body move to the node's `IncludeFilePaths`. The
code lives in the asset and is derived from the source the build key hashes, so an unchanged source
skips it with everything else. The exact code layout and the symbol mangling are on
[Functions](/en/docs/language/functions#generated-hlsl).

1.x wrote one `/DreamShaderGenerated/<basename>_<hash>.ush` per source. The virtual directory
`/DreamShaderGenerated` is still mapped to the **Generated Shader Directory** project setting (default
`Intermediate/DreamShader/GeneratedShaders`), and *Clean Generated Shaders* still deletes every `*.ush`
under it — but no compile writes there any more; a file found there was written by a 1.x build. A
material saved by a 1.x build may still have Custom nodes that include one; rebuilding the material
replaces them with nodes that carry their own code.

## Notes

- **The parse unit is the file.** <Since v="2.0.0" /> `import` inlines nothing: an imported `.dsh` is
  preprocessed and parsed on its own, and its declarations are declared into the importing file. A name
  declared twice is `DSH4210`, an import cycle `DSH4211`. A header cannot hold an asset block
  (`DSH2249`), so "one `Shader` per file" (`DSH2250`) means the file itself. The build key still covers
  every imported byte. See [Imports and Namespaces](/en/docs/language/imports).
- Every diagnostic carries the line and column of the construct it is about, in the file that construct
  is in: one raised inside an imported header names the header. Only a few file-level ones, such as an
  import that cannot be resolved, report line 1.
- Products are emitted in dependency order: a function another product of the same file calls is built
  first, so a `Shader` can call a `ShaderFunction` declared beside it. Otherwise the order is the order
  of declaration.
- Generation is editor-only. To write the same material in the 2.0 language, see
  [DreamShaderLang 2.0](/en/docs/language-v2) and [Migrating from 1.x](/en/docs/language-v2/migrate).

## Worked example

```c
// DShader/Materials/M_Emissive.dsm
import "Common.dsh";

ShaderFunction(Name="Functions/F_Tint")
{
    Inputs  { vec3 InColor; vec3 InTint; }
    Outputs { vec3 OutColor; }
    Graph   { OutColor = InColor * InTint; }
}

Shader(Name="Materials/M_Emissive")
{
    Properties { vec3 Tint = vec3(1.0, 0.4, 0.1); }
    Settings   { ShadingModel = "Unlit"; }
    Outputs    { vec3 Color; Base.EmissiveColor = Color; }
    Graph      { Color = F_Tint(vec3(1.0, 1.0, 1.0), Tint); }
}
```

One compile of that file produces:

```text
/Game/Functions/F_Tint            UMaterialFunction, saved
/Game/Materials/M_Emissive        UDreamShaderMaterialInstance + hidden UMaterial base, Ephemeral in the editor
```

and reports:

```text
Generated MaterialFunction /Game/Functions/F_Tint.F_Tint from I:/.../M_Emissive.dsm.
Generated Material /Game/Materials/M_Emissive.M_Emissive from I:/.../M_Emissive.dsm.
```
