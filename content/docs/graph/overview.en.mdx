A `Graph` block is where a DreamShaderLang file stops describing a material and starts *building*
one. Its body is a sequence of statements that the compiler lowers **once, in order, at generation
time** into the `UMaterialExpression` nodes of the target `UMaterial` or `UMaterialFunction`.

Nothing in a `Graph` body survives to runtime as code. What survives is the graph it built.

<Callout type="info">
Since <Since v="2.0.0" />, a `.dsm` / `.dsf` is read by the **legacy front end** and built by the
same 2.0 compiler that builds `.dss`. These six pages describe how the 1.x `Graph` language is built
**today**: the 1.x generator is gone, and what it silently truncated or narrowed is now either an
error with a `DSHnnnn` code, or built the way 1.x built it by a numbered legacy rule (L19, L22, L26,
L27, …) that says so. For loops, `?:` and `&&`, write [the 2.0 language](/en/docs/language-v2);
[`dsc migrate`](/en/docs/language-v2/migrate) rewrites a 1.x file for you.
</Callout>

## Graph is not the declaration language

The blocks around a `Graph` — `Shader(...)`, `Properties`, `Settings`, `Outputs`, `[Metadata]` — are
parsed by the declaration parser. The body of a `Graph` block is read token by token by the 2.0
statement and expression parser, and a legacy restriction pass then refuses what 1.x did not have.
They only look alike.

| | Declaration language | Graph language |
| :-- | :-- | :-- |
| Unit | blocks, sections, key/value entries | statements terminated by `;` (an `if` ends at its last `}`) |
| Keywords | block names, section names | `if` / `else`; `for`, `return`, `switch` and the other HLSL keywords are recognised, then refused |
| Case | section and block names have their own rules | keywords are case-sensitive; type tokens, constructors and `true` / `false` are not; other names match exactly, and a case-only match is used with the warning `DSH5275` |
| Literals | the declaration-level literal grammar | the 2.0 lexer: suffixes and integer kinds; hex is refused (`DSH2222`) |
| Unknown text | diagnosed | diagnosed too, one code per construct <Since v="2.0.0" /> — see [What Graph Is Not](/en/docs/graph/unsupported) |

A construct that is perfectly legal in `Properties` may mean something else entirely inside `Graph`.
When something in a `Graph` body behaves oddly, the rules on these six pages are the ones that apply —
not the ones on [Top-level Blocks](/en/docs/language/blocks).

## Where a `Graph` block may appear

| Block | `Graph` | `Code` |
| :-- | :-- | :-- |
| [`Shader`](/en/docs/language/blocks) | required, unless the `Outputs` section declares or binds something (`DSH2255` otherwise) | refused: `DSH2246` |
| `ShaderFunction` | optional; without one the body is empty | refused: `DSH2246` |
| `ShaderLayer` / `ShaderLayerBlend` | optional; without one the body is empty | refused: `DSH2246` |
| `VirtualFunction` | refused: `DSH2247` — it declares an existing asset, it does not build one | refused: `DSH2247` |
| [`Function` / `GraphFunction`](/en/docs/language/functions) | the body is HLSL, not a `Graph` block | — |

The section name is matched **case-insensitively**, and the `=` before the `{` is optional
<Since v="1.5.0" />, so `Graph = { … }` and `Graph { … }` are the same thing.

The same statement language is reused, in reduced form, in two other places:

| Place | Shape |
| :-- | :-- |
| An `Outputs` binding's right-hand side | one full expression, no statements |
| An `Outputs` declaration's `= <default>` | one expression: the initializer of a variable declared before the first `Graph` statement |

## The evaluation model

1. **The legacy front end reads the body into the 2.0 tree** <Since v="2.0.0" />. A `Shader` becomes
   one material function whose body is, in order: every `Outputs` declaration (with its initializer,
   or a zero of its type), the `Graph` statements, and the `Outputs` bindings as assignments to the
   material. A function block's `Graph` is the body of the function its `Inputs` and `Outputs` declare.
2. **The binder types every name and expression** before any node exists. A construct 1.x did not
   have, or one that does not type, stops the build with a code — a body is never half-built.
3. **Statements are lowered once each, top to bottom.** There is no loop construct, no `return`, no
   recursion, no re-entry. Statement *n* can only see values produced by statements 1 … *n*−1.
4. **Every expression is a typed value**: a number of 1–4 components (of kind `float`, `half`, `int`,
   `uint` or `bool`), a texture, a sampler, a `MaterialAttributes` value or a `Substrate` value. A
   variable name is bound to one such value.
5. **Passes run over the lowered graph**: constant folding, merging of identical nodes, and pruning of
   every node nothing reads. Only then does the emitter create the `UMaterialExpression` nodes.
6. **`Outputs` binding sources are evaluated last**, each as a full expression against the values the
   body left behind.

## What follows from that

### There is no runtime control flow

An `if` lowers **both** branches at build time. Both branch node sets exist in the finished material,
and one conditional node per changed variable (`If`, or `StaticSwitch` when the condition is a static
bool parameter) selects between them. An `if` is a select, not a jump — a branch that is never taken
still costs instructions. See [Control Flow](/en/docs/graph/control-flow).

### A declared variable is not storage

Assigning to a name rebinds it to a different node. The previously bound node stays in the graph if
something else still reads it, and is pruned otherwise. `a = a + 1;` is rewiring; `a++;` is the error
`DSH2207`.

### Identical subexpressions collapse

The deduplication pass merges nodes with the same operation and the same operands, so the same
literal, the same `A + B`, the same `UE.TexCoord(Index = 0)` produce **one** node no matter how many
times they are written. The pass sees the whole graph and is not scoped to blocks. Since
<Since v="2.0.0" />, what 1.x never shared — `Function` calls, sugar builtins such as `UE.TexCoord`,
`MaterialAttributes` nodes, `If` nodes — is merged too when equal. See
[Node reuse](/en/docs/graph/expressions#node-reuse).

### Some constructs create no nodes of their own

Grouping parentheses, `+x` and a scalar broadcast create no node; for the cost of a swizzle see
[Swizzles](/en/docs/graph/expressions#swizzles).

### Types are checked, widths included

Two operands of different widths, neither a scalar, are `DSH4226`; a wider value stored into a
narrower variable keeps its leading components with the info `DSH5289`; `int`, `uint`, `bool` and
`half` are kinds of their own to the compiler and floats in the graph. `7 / 2` is still `3.5` (legacy
rule L27). See [Conversions](/en/docs/graph/expressions#conversions).

### Unknown operators are refused, not dropped

1.x silently ended an expression at `%`, `&&`, `||`, `?:`, `[ ]`, `<<` and friends, so `a % b` built
`a`. Since <Since v="2.0.0" /> each is an error with a code (`DSH2200`–`DSH2222`). See
[What Graph Is Not](/en/docs/graph/unsupported).

## Comments and `#Region`

Comments are read by the lexer <Since v="2.0.0" />: `//` line comments and `/* */` block comments.
Block comments do not nest; the first `*/` closes, and one that never closes is `DSH2102`. A `//`
inside a string literal is not a comment. Every diagnostic line and column is the position in the
source file.

`#Region "Name"` and `#EndRegion` lines group the nodes produced by the statements between them into
a comment box in the generated graph. Each is a line of its own and a statement of the body
<Since v="2.0.0" />; regions nest. A `#Region` without a name, an `#EndRegion` with none open, a region
still open at the end of the body and any other `#` line are `DSH2216`–`DSH2219`, or `DSH1035` when
the preprocessor does not know the line. Full syntax is on [Layout and #Region](/en/docs/language/layout).

## Where diagnostics point

Every diagnostic is reported against the **source file**, at the construct it is about:

```text
<file>(<line>,<column>): DSHnnnn: <message>
```

The code is the contract; the wording may change. The line and column are those of the construct
itself, inside a section or an `if` body alike <Since v="2.0.0" /> — there is no `In Graph if body:`
prefix any more. A stage reports all of its errors, and a stage with errors stops the build before the
next one. The codes are listed in [Diagnostics](/en/docs/diagnostics).

## Example

```c
Shader(Name="Docs/M_Arithmetic")
{
    Properties = {
        vec3  A = vec3(1.0, 0.5, 0.2);
        vec3  B = vec3(0.1, 0.2, 0.3);
        float K = 2.0;
    }
    Settings = { Domain = "UI"; ShadingModel = "Unlit"; }
    Outputs  = { vec3 Color; Base.EmissiveColor = Color; }
    Graph = {
        vec3 Sum    = A + B;
        vec3 Diff   = A - B;
        vec3 Scaled = A * K;
        vec3 Ratio  = A / K;
        Color = Sum + Diff - Scaled + Ratio;
    }
}
```

Generated nodes:

```text
VectorParameter A, VectorParameter B, ScalarParameter K   (property nodes)
Add       (A, B)          -> Sum
Subtract  (A, B)          -> Diff
Multiply  (A, K)          -> Scaled
Divide    (A, K)          -> Ratio
Add       (Sum, Diff)
Subtract  (.., Scaled)
Add       (.., Ratio)     -> Base.EmissiveColor
```

Five statements, seven nodes, plus the three property nodes they read. No control flow, no execution
order beyond the order written, and nothing left over at runtime.
