---
title: Control Flow
description: if / else in a Graph block — a build-time select that builds both branches, one conditional node per changed variable, and the truthy form that means != 0 rather than > 0.
---

`if` / `else` is the only control-flow statement in the Graph language, and it is not a jump. Both
branches are lowered to nodes at generation time, both node sets stay in the finished material, and
**one conditional node per changed variable** — a `UMaterialExpressionIf`, or a
`UMaterialExpressionStaticSwitch` when the condition is a static bool parameter — selects between them.

## Synopsis

<Synopsis>
```c
if ( <condition> )
{
    <graph-statement> …
}
[ else
{
    <graph-statement> …
} ]

<condition> := <expression> [ { >= | <= | == | != | > | < } <expression> ]
```
</Synopsis>

`else if` chains are legal: an `else if` is an `if` statement in the `else` slot, so a chain is a tree of
nested statements, not a flat list.

## Requirements

| Rule | Detail |
| :-- | :-- |
| Condition parentheses | **Required** — `if x > 0 { }` is `DSH2157` |
| Body braces | **Required** on both branches — a single-statement body without braces is `DSH2209` |
| Statement terminator | **Not required** — the statement ends with the `}` of its last body, so no `;` follows it. A stray `;` after the `}` is an empty statement |
| Keyword case | **`if` and `else` are case-sensitive**, like every keyword. Type tokens, constructors and `true` / `false` are matched in any case; another name in the wrong case is used with the warning `DSH5275` |
| Body contents | every statement form is legal inside a branch: declarations, assignments, `MaterialAttributes` member writes, call statements and nested `if` |

<Callout type="warn">
`If (x) {}` and `ELSE {}` are not control flow. Because the keyword match is case-sensitive, `If (x)` is a
call to a function named `If`, and the `{` where that statement's `;` belongs is `DSH2154` — a code that
does not mention `if` at all. See [What Graph Is Not](/en/docs/graph/unsupported#wrong-case-keywords).
</Callout>

## The condition

The condition is one expression, read by the expression parser <Since v="2.0.0" /> (1.x split the text at
the first comparison operator before parsing either side). Comparison operators are not part of an
ordinary expression — this is the only place they are accepted.

| Operator | Meaning |
| :-- | :-- |
| `>` | left greater than right |
| `<` | left less than right |
| `>=` | left greater than or equal to right |
| `<=` | left less than or equal to right |
| `==` | left equal to right |
| `!=` | left not equal to right |
| *(none)* | the **truthy** form — see below |

How the condition is read:

1. The condition is parsed as one expression. A missing operand — `if ()`, `if (Mask >)` — is `DSH2151`
   <Since v="2.0.0" /> (1.x read `if (Mask >)` as `if (Mask != 0)`).
2. When the expression is a comparison, its two sides are the operands; anything else is the **truthy**
   form.
3. Each operand is a 1.x value expression: a second comparison, `&&` or `||` is `DSH2210`, and the other
   operators 1.x did not have are refused as anywhere else (`DSH2200`–`DSH2222`).
4. The binder types the operands: both must be numbers (`DSH4226` for a texture, a `MaterialAttributes` or
   a `Substrate` value), and the condition must be a single value — a comparison of two vectors is
   `DSH4260`.

## Truthy semantics

<Callout type="warn">
**`if (x)` is wired as `x != 0`, not as `x > 0`.** A *negative* value is truthy: `if (Height)` takes the
then-branch for `Height = -1.0` exactly as it does for `Height = 1.0`.

```c
// Written — both -1.0 and 1.0 take the then-branch.
if (Height) { Color = Hot; } else { Color = Cold; }

// What it builds:
if (Height != 0) { Color = Hot; } else { Color = Cold; }

// If you meant a sign test, say so:
if (Height > 0) { Color = Hot; } else { Color = Cold; }
```

This matches HLSL / C semantics and the decompiler's `!= 0` convention. Whenever the sign matters, write
the comparison out.
</Callout>

The right operand of a truthy condition is a `Constant` node holding `0`.

## `&&` and `||` are refused

<Callout type="warn">
Since <Since v="2.0.0" /> **`&&` and `||` are `DSH2210`**. 1.x silently dropped everything after the first
comparison, so `if (a > 0 && b > 0)` compiled as `if (a > 0)` with no diagnostic; a 1.x source that relied
on that now fails instead of quietly building half of its condition.

```c
// Refused (DSH2210); 1.x built if (Mask > 0.5).
if (Mask > 0.5 && Alpha > 0.5) { Color = Hot; } else { Color = Cold; }

// Write nested ifs instead:
if (Mask > 0.5) {
    if (Alpha > 0.5) { Color = Hot; } else { Color = Cold; }
} else {
    Color = Cold;
}
```

The same holds for `%`, `?:`, `[ ]`, `~`, `!` and the shift and bitwise operators anywhere in a condition:
each is an error with its code. See [What Graph Is Not](/en/docs/graph/unsupported#operators-1x-truncated).
</Callout>

## Node wiring

One conditional node is created **per merged variable**:

| Condition | Node |
| :-- | :-- |
| a comparison of two scalars | `If`: `A` receives the left operand, `B` the right one |
| truthy, or any other single value | `If`: `A` receives the value, `B` a `Constant` holding `0` |
| a `StaticBoolParameter` property, or a `StaticBool` function input | `StaticSwitch`: `Value` receives the parameter, `A` (true) the then-value, `B` (false) the else-value |

The three result pins of an `If` are wired from the branch values:

| Operator | `AGreaterThanB` | `AEqualsB` | `ALessThanB` |
| :-- | :-- | :-- | :-- |
| `>` | then | else | else |
| `<` | else | else | then |
| `>=` | then | then | else |
| `<=` | else | then | then |
| `==` | else | then | else |
| `!=` | then | else | then |
| truthy | then | else | then |

A `bool` property that is not a `StaticBoolParameter` — a plain `StaticBool` or `bool` entry — is a dynamic
parameter <Since v="2.0.0" />, and `if` on it is the truthy `If`. See
[Properties](/en/docs/parameters/properties).

The result is as wide as the wider of the two branch values. It is never a texture object.

## Both branches are always built

There is no dead-code elimination and no build-time decision on the condition, even a constant one.
Lowering an `if` does the following, in order:

1. Lower the condition once.
2. Lower every then-statement, starting from the values as they stood before the `if`.
3. Lower every else-statement, starting from the same values.
4. Merge (below).

In practice:

- **Every node in both branches that feeds a merged value exists in the generated material.** A branch
  that is never taken at runtime still costs shader instructions. `if` is a select, not a jump.
- An error inside either branch fails the build, even in a branch a constant condition could never reach.
  Each error is reported at its own line and column.
- A variable declared inside a branch is local to it <Since v="2.0.0" />: it is not merged, and the name is
  unknown after the `if`. See [Statements](/en/docs/graph/statements#scope).
- Identical nodes in the two branches and after the merge are merged by the deduplication pass. See
  [Node reuse](/en/docs/graph/expressions#node-reuse).
- The condition's operands are shared, but **N** merged variables make **N** conditional nodes.
- A parameter first read inside a branch and read again after the `if` is one node <Since v="2.0.0" />
  (1.x left a duplicate parameter node).

## The merge

A variable is merged when it was declared **before** the `if` and either branch changed it. Properties are
never merged: they are inputs, and reading one inside a single branch changes nothing.

| Variable | Result |
| :-- | :-- |
| changed in both branches | one conditional node over the two values |
| changed in one branch only | one conditional node over the changed value and the value from before the `if` |
| declared inside a branch | dropped at the end of the branch; nothing is merged |
| had no value before the `if` and is assigned in one branch only (a function output not yet written, for instance) | marked; a later read is `DSH4372` |
| a `MaterialAttributes` value | merged attribute by attribute, one conditional node per attribute the branches disagree on |

<Callout type="info">
A variable's value is converted to its declared type at every assignment, so the two branch values of one
variable always have the same type — the merge itself converts nothing.
</Callout>

<Callout type="warn">
**Branch-local declarations stay in their branch** <Since v="2.0.0" />. 1.x merged a name declared in a
branch, demanded it in the other branch too, and kept it after the `if`. Now a `float3 Temp = …;` declared
in one branch is gone after that branch, and the same name declared in both branches is two unrelated
variables. Declare the variable **before** the `if` when the code after it needs it:

```c
// 'Blend' is local to each branch: Color = Blend; after the if is DSH4200.
if (Mask > 0.5) { float3 Blend = float3(1.0, 0.0, 0.0); Color = Blend; }
else            { float  Blend = 0.25;                  Color = float3(Blend, Blend, Blend); }

// One declaration, one type, assigned in both branches.
float3 Blend = float3(0.0, 0.0, 0.0);
if (Mask > 0.5) { Blend = float3(1.0, 0.0, 0.0); }
else            { Blend = float3(0.25, 0.25, 0.25); }
Color = Blend;
```
</Callout>

## What cannot be selected

| Value kind | Behaviour |
| :-- | :-- |
| scalar / vector, 1–4 components | selected normally |
| `MaterialAttributes` | selected attribute by attribute; a different **whole** set in each branch is `DSH4375` |
| texture object, sampler | rejected — `DSH4379` |
| `Substrate` | a `StaticSwitch` under a static condition; otherwise a `Substrate.Select` node <Since v="5.6" ue />, or `DSH4378` on an older engine. `DSH4380` warns when the two values are different kinds of BSDF |

To branch on a texture, sample both and select between the samples, or hand the choice to a
`StaticSwitchParameter` applied to the sampled results. See
[Calls](/en/docs/graph/calls#staticswitchparameter).

## Example

```c
Shader(Name="Docs/M_IfElse")
{
    Properties {
        float Mask = 0.6;
        vec3  Tint = vec3(1.0, 0.2, 0.2);
    }

    Settings {
        Domain       = "UI";
        ShadingModel = "Unlit";
    }

    Outputs {
        vec3 Color;
        Base.EmissiveColor = Color;
    }

    Graph {
        if (Mask > 0.5) {
            Color = Tint;
        } else if (Mask > 0.25) {
            Color = Tint * 0.5;
        } else {
            Color = vec3(0.0, 0.0, 0.0);
        }
    }
}
```

```text
VectorParameter  Tint
ScalarParameter  Mask
Constant         0.5                 (shared)
Constant         0.25
Multiply         Tint * 0.5
Constant3Vector  (0,0,0)             (folded literal)
If               A=Mask B=0.25  ->   inner else-if merge of 'Color'
If               A=Mask B=0.5   ->   outer merge of 'Color'
```

Both `If` nodes exist because the `else if` is a nested `if`, and every branch's nodes are in the
material regardless of the runtime value of `Mask`.
