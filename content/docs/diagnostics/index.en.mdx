Every **diagnostic** a compile raises carries a stable `DSHnnnn` code <Since v="2.0.0" />: one code, one message, one
severity, owned by one source file, at the line and column of the construct it is about. **The code is the contract;
the wording is not.** This page explains where diagnostics appear and how to read them, lists the ones you are most
likely to hit by stage, and maps the old messages of the 1.x generator to the codes raised today.

| Item | Value |
| :-- | :-- |
| Produced by | `DreamShaderLang` — the preprocessor, both front ends, the binder, the IR and its validator · `DreamShaderCompiler` — the pipeline, the include resolver, the emitter, the asset layer · `DreamShaderEditor` — the bridge, the commandlet verbs and the tools |
| Log category | `LogDreamShader` |
| Wire form | `<file>(<line>,<column>): DSHnnnn: <message>`, English whatever the editor's language |
| Severity | `error`, `warning` or `info` — a compile's records keep their own <Since v="2.1.0" />; the few records a compile does not explain are `error` |
| Bridge artifacts | `<Project>/Saved/DreamShader/Bridge/diagnostics.json`, `.../Bridge/diagnostics/`, `.../Bridge/bridge.db` |
| Full catalogue | [`Docs/diagnostics/README.md`](https://github.com/TypeDreamMoon/DreamShader/blob/main/Docs/diagnostics/README.md) in the plugin repository — every code with its severity and message; each code has a section on `DSH1xxx.md` … `DSH9xxx.md` with every message raised under it, a cause and a fix |

<Callout type="info">
**Through 1.9.x most messages had no code.** The 1.x parser coded its own, the 1.x generator's ~560 raise sites
reported bare text, and this page catalogued that text verbatim. The generator and the parser were removed in 2.0.0,
and none of those strings is raised any more. If you have one in an old log or a search result,
[1.x messages and their codes](#1x-messages-and-their-codes) maps the common ones.
</Callout>

## Where diagnostics appear

| Surface | What it shows |
| :-- | :-- |
| **Output Log** | the compile's report under `LogDreamShader`: at `Error` on failure — every record as a wire line, errors first, then warnings, then notes — and at `Display` on success — the `Generated …` / `Skipped …` lines, then a `Warnings:` block |
| **[Material Content Browser](/en/docs/tools/editor#material-content-browser)** | each source's records, read from the bridge's diagnostics store; the first error is shown on the source's row |
| **`Bridge/diagnostics.json`** | `{ version, updatedAtUtc, files[] }`, one entry per file |
| **`Bridge/diagnostics/`** | one `<md5-of-normalized-path>.json` shard per file plus `index.json`; stale shards are deleted on every write |
| **`Bridge/bridge.db`** | SQLite table `diagnostics(path, json, updated_at_utc)`, replaced wholesale in one transaction |
| **`-DiagnosticsOut=<file>`** | one commandlet run's diagnostics as JSON (schema `dreamshader-diagnostics`) — see [Commandlet](/en/docs/tools/commandlet#diagnostics) |
| **VSCode / Rider squiggles** | rendered by the extensions from the three bridge artifacts above — **extension side**, not the plugin |

All three bridge sinks are written together on every update, so they never disagree. The Output Log is a separate path
and is the only surface that shows *success* lines.

Diagnostics are owned by the source and by the **run** that produced them. There are three kinds of run: the compile
of a source, the shader compile of one material it generated, and the startup VirtualFunction scan of a file.

| Run | What it replaces |
| :-- | :-- |
| the compile of `A.dsm` | exactly what A's previous compile filed — against A, and against any header A imports. What `B.dsm` filed against the same header stays <Since v="2.1.1" />. It also retires what the startup scan said about A and its headers |
| the shader compile of one material | that material's shader-compile records, when its shader compile finishes — ticks after the compile that generated it; never the compile's own warnings |
| the startup VirtualFunction scan | its records for the file it scanned |
| deleting a file | everything the file owns, and every record filed against it, whoever filed it |

Within one file the records run compile first, then shader compile, then the VirtualFunction scan, by source within
each, so the first error of a file is always its compile's.

<Callout type="warn">
The bridge never runs inside a commandlet. `-run=DreamShader`, `-run=Cook` and any other commandlet process writes no
`diagnostics.json`, no shards and no `bridge.db` rows; the messages exist only in the log (and in a `-DiagnosticsOut`
file). The bridge is also suppressed by `-NoDreamShaderEditorBridge`. See [Commandlet](/en/docs/tools/commandlet).
</Callout>

## Severity

<Since v="2.1.0" />

A compile files its own records with the severity each was raised at — a failed compile all of them, a successful one
its warnings and notes. Before 2.1.0 every stored diagnostic was `error`, and a successful compile's warnings reached
only the Output Log, where the editor extensions could not see them.

| Severity | When | Example |
| :-- | :-- | :-- |
| `error` | the compile fails; the stages after this one do not run | `DSH4200` undeclared name |
| `warning` | the compile succeeds, with something you should know | `DSH2251` old spelling, `DSH7233` slider range dropped, `DSH5277` GLSL spelling |
| `info` | the compile succeeds; it says out loud what 1.x did in silence | `DSH5283` a call declared its out target, `DSH5289` a wider value cut to its leading components |

The records a compile does not explain — `generate-error`, `material-compile`, `virtual-function-sync` — are `error`.
Log-only warnings that are not a compile's records (`UE_LOG(LogDreamShader, Warning, …)`) never enter the store. A
client treats a missing or unknown severity as an error.

## Reading a message

A diagnostic is printed MSVC-style, with its code:

```text
I:/Project/DShader/Materials/M_Sample.dsm(8,19): DSH4200: 'Tin' is not declared in this scope.
```

| Diagnostic | Where its position comes from |
| :-- | :-- |
| a compile's record | the line and column of the construct, from the token it was raised at — in a section body, in a `Graph`, in an imported header alike. A record raised inside a header names the **header**, not the file that imports it |
| about a file as a whole — an include that cannot be resolved, a source the compiler does not build | line 1, column 1 of the file |
| material compile | the engine's own `<path>(<line>,<col>): ` prefix, re-parsed and re-attributed to the source line it came from |
| `generate-error` — a failure the records do not explain | recovered from a `<path>(<line>,<column>): <message>` line; otherwise `1,1` |

<Since v="2.0.0" /> Each file is lexed and parsed on its own, so a position is never mapped back from an assembled
text. Through 1.9.x a parse error carried a `near index {Index}` offset into the import-inlined text, a position inside
a section body was wrong, and most statement-level messages had no position at all.

A stage reports **all** of its errors — the parser and the binder keep going after one — and a stage with errors stops
the pipeline before the next stage: a file with a syntax error is not bound, a file that does not bind is not emitted.

## `DSHnnnn` codes

The leading digit is the stage that raises it. Each band has a page in the plugin repository; follow the band:

| Band | Stage |
| :-- | :-- |
| [`DSH1xxx`](https://github.com/TypeDreamMoon/DreamShader/blob/main/Docs/diagnostics/DSH1xxx.md) | the preprocessor (`#if`, `#define`), asset references in a 1.x texture default |
| [`DSH2xxx`](https://github.com/TypeDreamMoon/DreamShader/blob/main/Docs/diagnostics/DSH2xxx.md) | the lexer and the parsers — `DSH2200`–`DSH2258` are the legacy front end's: 1.x `Graph` statements and top-level blocks |
| [`DSH3xxx`](https://github.com/TypeDreamMoon/DreamShader/blob/main/Docs/diagnostics/DSH3xxx.md) | declarations, `#pragma`, `///` blocks; `DSH3250`–`DSH3278` the legacy front end's sections |
| [`DSH4xxx`](https://github.com/TypeDreamMoon/DreamShader/blob/main/Docs/diagnostics/DSH4xxx.md) | the binder (names, types, statements), the IR validator, lowering refusals |
| [`DSH5xxx`](https://github.com/TypeDreamMoon/DreamShader/blob/main/Docs/diagnostics/DSH5xxx.md) | `UE.*` / `Substrate.*` calls and the node catalog; `DSH5250`–`DSH5292` the 1.x call spellings and the numbered **legacy rules** |
| [`DSH6xxx`](https://github.com/TypeDreamMoon/DreamShader/blob/main/Docs/diagnostics/DSH6xxx.md) | function kinds, inlining, `/// @custom` HLSL; `DSH6300`–`DSH6330` 1.x `Function` / `GraphFunction` / `Namespace` / `VirtualFunction` |
| [`DSH7xxx`](https://github.com/TypeDreamMoon/DreamShader/blob/main/Docs/diagnostics/DSH7xxx.md) | uniforms, directives, `#pragma material`, the material settings writer, `.dsi`, `.dsp` checks |
| [`DSH8xxx`](https://github.com/TypeDreamMoon/DreamShader/blob/main/Docs/diagnostics/DSH8xxx.md) | the emitter, the asset layer, the include resolver (`DSH8291`–`DSH8295`), Custom Pass emission |
| [`DSH9xxx`](https://github.com/TypeDreamMoon/DreamShader/blob/main/Docs/diagnostics/DSH9xxx.md) | the tools — `check`, `dump-ir`, the decompiler, `migrate`, navigation, `pass-registry` |

Each code's section has every message raised under it, the places that raise it, a cause and a fix. The site has no
page per code; for a code not listed below, search its band's page for it.

### Legacy rules

A **legacy rule** (`DSH5275`–`DSH5292`) is something 1.x did that a 1.x source still gets, said out loud: a name
matched only by case (`DSH5275`, `DSH5276`), a GLSL spelling (`DSH5277`), a wider vector cut down where a narrower one
goes (`DSH5289`), an assignment that declares its variable (`DSH5292`). It is a warning or an info on a `.dsm` /
`.dsf` and never appears in a `.dss` — there the same text is an error (a GLSL spelling in a `.dss` is `DSH4250`, for
example). [`dsc migrate`](/en/docs/language-v2/migrate) writes each one out as explicit 2.0 text.

## Common diagnostics

The codes a working project runs into most, grouped by stage. The messages are the plugin's current templates, with
`{…}` for what is filled in at run time; a code may have other wordings as well, and the plugin's page is authoritative.

## What 1.x accepted in silence

Conditions the 1.x generator accepted without a word — and built something other than what the text says, or dropped
what it said. <Since v="2.0.0" /> Each is a diagnostic now.

| 1.x text | 1.x did | Today |
| :-- | :-- | :-- |
| `a % b`, `a & b`, `a \| b`, `a ^ b`, `a << b` in a `Graph` expression | stopped reading at the operator: the expression was `a` | `DSH2201` |
| `a ? b : c`, or `a < b` outside an `if` condition | the same: the expression was `a` | `DSH2200` |
| `v[0]` | dropped the index and everything after it | `DSH2202` |
| `if (a > 0 && b > 0)` | tested `a > 0` only | `DSH2210` |
| `(float3)x` | had no casts | `DSH2203` |
| `a += b` | read a declaration of a variable named after the operator | `DSH2205` |
| `x++` | had no such operator | `DSH2207` |
| `a + b;` as a statement | built nodes nothing read | `DSH2211` |
| `0x10` in a `Graph` expression | read it as a different number | `DSH2222` |
| `1abc` or `0.5.5` as a number | used the leading digits | `DSH2105` |
| an unterminated `/* …` | consumed the rest of the file | `DSH2102` |
| an attribute written twice, `Shader(Name="A", Name="B")` | kept the later value | the warning `DSH2244`, later value kept |
| a `Settings` key written twice | kept the later value | the warning `DSH3262`, later value kept |
| an unknown key in a material-function `Settings` | ignored it | the warning `DSH3263`, still ignored |
| a positional argument on a `UE.*` call that takes none | ignored it | the warning `DSH5254`, still dropped |
| a default on a function's `Outputs` entry | ignored it | the warning `DSH3273`, still dropped |
| a second `Graph` or `Layout` section | kept the later one | the warning `DSH2258`, later one kept |
| a `ShaderFunction` with the name of a builtin, called from `Graph` | called the builtin | `DSH6206` at the declaration |
| `dot(vec3Value, vec2Value)` | accepted it; Unreal's own material translation failed later | `DSH4226` |

What 1.x documented and a 1.x source still relies on — a name in another case, a GLSL spelling, a `float4` written
into a `float3` place — keeps building, as a [legacy rule](#legacy-rules) that says so.

## VirtualFunction sync

The startup service that re-reads every `VirtualFunction` declaration and refreshes it from its `UMaterialFunction`
asset, plus the editor actions on the Material Function toolbar and context menu. These messages have no `DSHnnnn`
code, except `DSH9001` for a source that uses `#if` — the sync rewrites a source in place at byte offsets, cannot tell
which branch a definition belongs to, and refuses to touch it.

Sync diagnostics reach the store with `stage = virtualFunctionSync`, `code = virtual-function-sync` and
`source = DreamShader VirtualFunction`. The editor-action messages are toast notifications and log lines; they are not
stored.

| Message | Cause | Fix |
| :-- | :-- | :-- |
| `VirtualFunction '{Name}' references missing MaterialFunction '{Path}'.` | the asset did not load | restore the asset, or update `Options.Asset` |
| `VirtualFunction '{Name}' could not be refreshed from MaterialFunction '{Path}': {Detail}` | the declaration builder failed | see the inner message |
| `VirtualFunction '{Name}' asset reference is invalid: {Detail}` | `Options.Asset` did not resolve | fix the `Path( … )` |
| `DreamShader could not read VirtualFunction source file '{File}'.` | the source file is unreadable; reported at line 1, column 1 | check file locks and permissions |
| `DreamShader failed to update VirtualFunction source file '{File}'.` | the refreshed declaration could not be written back; reported at line 1, column 1 | check file locks and source control |
| `MaterialFunction '{Name}' does not expose any outputs.` | the asset has no `FunctionOutput` node | add an output to the material function |
| `DreamShader could not find a VirtualFunction definition for {Asset}.` | *Open VirtualFunction* on an asset with no declaration | use *CreateVirtualFunction* instead |

<Callout type="info">
The sync service finds a declaration by the bare keyword `VirtualFunction`, **case-sensitively**, with identifier
boundaries on both sides — the same spelling the legacy front end requires of a block word. A lower-case
`virtualfunction` is invisible to both.
</Callout>

## One error, four surfaces

A typo inside a `Graph` block, as it reaches each surface.

```c
// DShader/Materials/M_Sample.dsm
Shader(Name="Materials/M_Sample")
{
    Properties = { vec3 Tint = vec3(1.0, 0.4, 0.1); }
    Outputs    = { vec3 Color; Base.EmissiveColor = Color; }
    Graph      = {
        vec2 UV = UE.TexCoord(Index = 0);
        Color   = Tin * UV.x;          // typo: Tin, not Tint
    }
}
```

Output Log:

```text
LogDreamShader: Error: I:/Project/DShader/Materials/M_Sample.dsm(8,19): DSH4200: 'Tin' is not declared in this scope.
```

`Saved/DreamShader/Bridge/diagnostics.json`:

```json
{
  "version": 1,
  "updatedAtUtc": "2026-10-04T11:04:22Z",
  "files": [
    {
      "path": "I:/Project/DShader/Materials/M_Sample.dsm",
      "diagnostics": [
        {
          "message": "'Tin' is not declared in this scope.",
          "detail": "I:/Project/DShader/Materials/M_Sample.dsm(8,19): DSH4200: 'Tin' is not declared in this scope.",
          "stage": "bind",
          "code": "DSH4200",
          "line": 8,
          "column": 19,
          "severity": "error",
          "source": "DreamShader Lang2"
        }
      ]
    }
  ]
}
```

The same record is written to `Bridge/diagnostics/<md5>.json` and to the `diagnostics` table of `Bridge/bridge.db`,
and appears on the source's row in the Material Content Browser — the same data the VSCode and Rider extensions use
for their squiggles. `stage` follows from the code's band: `preprocess`, `parse`, `bind`, `ir`, `generate` or `tools`.

## Fixing in order

When one file reports a wall of messages, fix them top-down. A stage with errors holds back the stages after it, so
the next layer's messages appear once the layer above is clean.

<Steps>

<Step>
**Preprocessing and parsing first (`DSH1xxx`, `DSH2xxx`).** Balance braces, quotes and parentheses, and check keyword
case. If the file does not parse, nothing is bound.
</Step>

<Step>
**Then includes and unknown names (`DSH8292`, `DSH4200`, `DSH4208`).** Usually one missing `import` or one typo —
2.0 names are case-sensitive.
</Step>

<Step>
**Then types and signatures (`DSH42xx`, `DSH5xxx`, `DSH6xxx`).** Component mismatches, call arguments, node arguments.
</Step>

<Step>
**Then generation (`DSH8xxx`).** The ownership guard, an open editor, divergence and save failures — these mean the
source is right and the target is not.
</Step>

<Step>
**Unreal's own material compile last.** These carry the engine's `<path>(<line>,<col>)` prefix, re-attributed to your
source, with the code `material-compile`. They are the only messages DreamShader did not produce.
</Step>

</Steps>
