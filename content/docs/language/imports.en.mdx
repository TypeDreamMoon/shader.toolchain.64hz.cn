title: Imports and Namespaces
description: How import makes a .dsh header's declarations visible in the current file — recognition, specifier normalisation, source roots, how a header is read, and namespaces across files.
---

`import` makes the declarations of a `.dsh` header visible in the current file. It is a token of the
language and a top-level declaration, read by the legacy front end; the binder finds the header
through the include resolver, preprocesses and parses it on its own, and declares its names into the
current file <Since v="2.0.0" />. Through 1.9.x the editor's source loader stripped `import` lines
before parsing and pasted the header's text in.

```text
<file>.dsm
  │
  ├─ preprocessor          evaluates #if line by line; an import in an untaken branch is never read
  │
  ├─ legacy front end      blocks, sections, Graph statements, imports  ->  the 2.0 tree
  │
  ├─ binder                resolves each import; a header is preprocessed and parsed on its own,
  │                        and its declarations are declared into this file
  │
  └─ IR / emitter          material nodes  ->  asset
```

A `.dss` spells the same thing `#include "…"`, and takes `import "…";` as well.

## Syntax

<Synopsis>

```c
import "<path>" [;]
import '<path>' [;]          // in a .dsm, .dsf or .dsh

<path> := a path to a .dsh, relative to this file or to its source root,
          or "/"-anchored; the ".dsh" may be left off
```

</Synopsis>

The `;` is optional <Since v="1.2.2" />. `import` is lower case; another casing reads the same, with
the warning `DSH2253`.

```c
import "Shared/Common";                                   // -> Shared/Common.dsh in the file's own root
import '@typedreammoon/dream-noise/Library/Noise.dsh';    // -> <root>/Packages/@typedreammoon/…
import "../Lib/Color.dsh"                                 // -> relative to the importing file
import "/Shared/Toon.dsh";                                // -> own root first, then every other root (since 2.0.0)
```

### Recognition

`import` is a token, read by the parser like any other top-level declaration <Since v="2.0.0" />; the
1.x rule that recognized it line by line in the raw text is gone.

| Rule | |
| :-- | :-- |
| where | at the top level of the file, between blocks |
| comments | ordinary comments: an `import` inside `/* … */` or after `//` is commented out (the 1.x loader honoured one inside `/* … */`) |
| the path | a string: `"…"`, with the usual escapes; in a 1.x file or a `.dsh` also `'…'` on one line |
| `;` | optional |
| `#if` | resolved first, by the [preprocessor](/en/docs/language/lexical#preprocessor): an `import` in a branch that is not taken is not read |

| Refused | Code |
| :-- | :-- |
| `import` not followed by a string | `DSH2252` |
| a path that names a `.dsf` or a `.dsm` — a material or function file is compiled on its own, never included | `DSH2252` |
| a root-qualified path (`Project:Shared/Common.dsh`, `Plugin.X:…`) | `DSH2252` |
| a path that resolves to a file that is no `.dsh` (or `.dss`) | `DSH8295` |

<Callout type="info">

The editor's **dependency scanner** still reads `import` lines as text, to know which sources to
recompile when a header is saved: a trimmed line that starts with `import`, ignoring case, then a
`"…"` or `'…'` path, an optional `;` and nothing but a `//` comment. It reads the raw file, every `#if`
branch included, so a header imported only from an untaken branch still triggers a rebuild of its
importers. That is deliberate: a needless rebuild costs seconds, a missed one leaves a stale asset.

</Callout>

## Specifier normalisation

| # | Step |
| :-- | :-- |
| 1 | trim leading and trailing whitespace |
| 2 | replace every `\` with `/` |
| 3 | strip **all** leading `./` sequences |
| 4 | if the result has no extension at all, append `.dsh` |

So `import "Shared/Common"` and `import "Shared/Common.dsh"` are the same directive.

<Callout type="info">

Step 4 asks whether the path has an extension, not whether it has a known one, and it looks only at
the last path segment. `Shared/Common.v2` counts as "already has an extension", so no `.dsh` is
appended and the specifier resolves only if a file of exactly that name exists. A `.` in a
*directory* component — `@scope/pkg.v2/Lib` — does not count, and `.dsh` is still appended.

</Callout>

## Resolution

| Path | Resolved against |
| :-- | :-- |
| an absolute file path that exists | that file |
| `/`-anchored <Since v="2.0.0" />: `/Shared/Common.dsh`, or `/Game/Shared/Common.dsh` | the anchor (`/` or `/Game/`) dropped, then the importing file's own root — its source directory, then its packages directory — then every other root's two directories, in root order; the first file that exists wins. Never relative to the importing file |
| anything else | the three candidates below |

The three candidates are tried in order. Each is paired with a **containment root**; a candidate
resolving outside its root is skipped rather than reported, and the first candidate that exists on
disk wins.

| # | Candidate | Containment root |
| :-- | :-- | :-- |
| 1 | `<directory of the importing file>/<specifier>` | the longest source or packages directory, across every root, that contains the importing file; the importing file's own directory when it is under none |
| 2 | `<owning root's source directory>/<specifier>` | that source directory |
| 3 | `<owning root's packages directory>/<specifier>` | that packages directory |

| Directory | Default | Project setting |
| :-- | :-- | :-- |
| Project source | `<Project>/DShader` | *Source Directory* |
| Plugin source <Since v="1.6.0" /> | `<Plugin>/DShader` | *Scan Plugin Source Directories* |
| Packages | `<source directory>/Packages` | derived; not separately configurable |

A path that resolves nowhere is `DSH8292`, naming the reason.

### Source roots

<Since v="1.6.0" />

Candidates 2 and 3 belong to the **owning root** of the importing file — the source root the file
sits under.

<Callout type="warn">
**A relative specifier never leaves its root.** A `.dsm` under `Plugins/MoonToon/DShader` cannot reach
`<Project>/DShader` by writing `Shared/Common.dsh`, and vice versa.

The rule exists so that adding a plugin cannot change what an existing import means. Were the project
root a global fallback, two plugins shipping `Shared/Common.dsh` would resolve by scan order, and
disabling a plugin would silently redirect another root's imports.
</Callout>

A file under **no** root — a test fixture, a commandlet `-Source` pointing outside the tree — takes
the project's source and packages directories for candidates 2 and 3, which is what every file did
before roots existed.

### Crossing a root deliberately

From 1.6.0 through 1.9.x a root qualifier and a `:` — `Project:Shared/Common.dsh`,
`Plugin.MoonToon:Shared/Toon.dsh` — pointed an import at another root's source and packages
directories. An `import` refuses that form now (`DSH2252`) <Since v="2.0.0" />. A header another root
ships is reached:

- by a `/`-anchored path, which looks in the importing file's own root first and then in every other
  root, so a file of the same name in the own root wins;
- by copying it into this root;
- or through a [package](/en/docs/tools/packages).

<Callout type="warn">
**A plugin that reaches into the project root is no longer self-contained**: ship it to another
project and the import dangles.
</Callout>

The containment comparison is case-insensitive on every platform; whether a candidate is then found
still follows the file system's own case behaviour.

The containment check is what stops a relative specifier from climbing out of the tree. `..` segments
are resolved *before* the check, so:

- from a file directly under `DShader`, `import "../Secret.dsh"` resolves above the source directory
  and candidate 1 is skipped; candidates 2 and 3 collapse the same `..`, land outside their roots, and
  are skipped too;
- from a file under `DShader/Packages/@scope/pkg/`, `..` may traverse anywhere inside
  `DShader/Packages`, because that is the containment root chosen for it;
- for a source file under neither directory, the containment root is its own directory, so no `..`
  specifier can resolve through candidate 1.

### Package-style paths

`@scope/name/…` is **not** a distinct path syntax. `@` is an ordinary directory-name character, and
`"@typedreammoon/dream-noise/Library/Noise.dsh"` resolves through candidate 3 simply because
`DShader/Packages/@typedreammoon/dream-noise/Library/Noise.dsh` exists on disk. There is no scope
registry, no version resolution and no special-cased root.

<Callout type="info">

Candidates 1 and 2 are still tried first, so a file of the same name next to the importing file, or
under `DShader` itself, **shadows** the package copy.

</Callout>

See [Packages](/en/docs/tools/packages) for the directory layout this convention assumes.

## How a header is read

Nothing is inlined <Since v="2.0.0" />. Each header is read on its own and its declarations are added
to the importing file's.

| Behaviour | Rule |
| :-- | :-- |
| preprocessing | each header is preprocessed **on its own** against the compile's define table: a `#define` in a header does not reach the file that imports it. A header whose `#if` fails is `DSH8291` |
| parsing | each header is parsed on its own, in its own dialect: a `.dsh` may hold 1.x blocks and 2.0 declarations side by side, whichever kind of file imports it. A syntax error in a header is reported at its own line, and the import is then `DSH8294`; one that cannot be read is `DSH8293` |
| names | every declaration of the header — and of the headers it imports — is visible in the importing file. A name declared twice, in the header and the importing file or in two headers, is `DSH4210` |
| diamonds | a header reached twice is declared once |
| cycles | a header that imports itself, directly or through another, is `DSH4211` |
| assets | none: a header holds no asset block (`DSH2249`), so an import adds names, never an asset, and a file still holds at most one `Shader` (`DSH2250`) |
| rebuilds | the preprocessed text of every header a compile read is part of that source's build key, and saving a header queues every source that imports it |

<Callout type="info">

**Through 1.9.x** the loader pasted the whole import closure into one text before parsing, so the "one
`Shader`" rule spanned the closure, a `.dsh` could import a `.dsf` and compile its `ShaderFunction`
blocks as part of the importing file, and every position had to be mapped back from the assembled
text. None of that applies any more.

</Callout>

## Namespaces across files

`Namespace` is not a module system and has nothing to do with `import`. The namespaces of an imported
header are declared into the importing file and visible with no extra declaration — and they collide
across files exactly as they would within one.

```c
// DShader/Lib/Common.dsh
Namespace(Name="Common")
{
    Function ApplyTint(in vec3 color, in vec3 tint, out vec3 result) {
        result = color * tint;
    }
}
```

```c
import "Lib/Common.dsh";

Graph = {
    vec3 Tinted;
    Common::ApplyTint(Base, Tint, Tinted);
}
```

| Rule | Consequence |
| :-- | :-- |
| Re-opening is allowed and unchecked | `Namespace(Name="Common")` in two imported headers both prefix `Common::`. |
| Members are reached only by the qualified name (or its flattened `Common_ApplyTint`) | No `using`, no name import, no unqualified fallback. |
| An `import` stands at file scope only | Inside a `Namespace` body it is `DSH6310` <Since v="2.0.0" />. |
| Duplicate qualified names are found when the file is bound | `DSH4210`, naming the files of both declarations. |

Declaration rules, `::` resolution and body normalisation: [Functions](/en/docs/language/functions#namespace).

## Source-line mapping

There is nothing to map any more <Since v="2.0.0" />. A diagnostic carries the file it was raised in —
the header, for an error inside one — and the line and column of the construct, and is printed
`<file>(<line>,<column>): DSHnnnn: <message>`. Through 1.9.x positions came from a `near index` offset
into the assembled text and were unreliable inside sections; that mechanism is gone.

## Organising a project

| Change | What recompiles |
| :-- | :-- |
| a `.dsm` | that material, and every function asset declared in the file |
| a `.dsf` | the function assets it declares |
| a `.dsh` | every `.dsm` / `.dsf` (and `.dss`) that imports it, directly or transitively |
| a package file | the sources that import it |

A stable entry header per project keeps the graph shallow:

```c
// DShader/Shared/Common.dsh
import "Shared/Color.dsh";
import "Shared/Texture.dsh";

Namespace(Name="Project")
{
    Function ApplyTint(in vec3 color, in vec3 tint, out vec3 result) {
        result = color * tint;
    }
}
```

```c
// every material imports just one file
import "Shared/Common.dsh";
```
