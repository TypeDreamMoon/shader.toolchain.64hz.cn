title: Source Files
description: The three 1.x file kinds, what each may declare, how that rule is enforced, and how a file is compiled together with the headers it imports.
---

DreamShaderLang 1.x lives in plain text files of three kinds. All three are read into tokens by one
lexer, read by the **legacy front end** into the same tree a `.dss` makes, and built by the 2.0
compiler <Since v="2.0.0" />. The extension decides two things — what the file is allowed to declare,
and whether compiling it produces an asset.

| Extension | Name | Role |
| :-- | :-- | :-- |
| `.dsm` | Dream Shader Material | Material entry point. At most one `Shader` block per file, with function and layer blocks beside it if you like. |
| `.dsf` | Dream Shader Function <Since v="1.3.5" /> | Asset entry point for material functions and layers. |
| `.dsh` | Dream Shader Header | Shared declarations only, 2.0 declarations included. Generates nothing; consumed through `import`. |

Extensions are compared case-insensitively, so `M_Water.DSM` is a material file.

<Callout type="info">

New sources are written in [DreamShaderLang 2.0](/en/docs/language-v2) (`.dss`). A 1.x source keeps
building through the same compiler, and [`dsc migrate`](/en/docs/language-v2/migrate) rewrites one as
`.dss`, proving the rewrite builds the same graph.

</Callout>

## Synopsis

<Synopsis>

```c
// <name>.dsm — Dream Shader Material
[ import "<header>.dsh" ; ]…
[ Shader( Name = "…" [, Root = "…"] ) { … } ]          // at most one per file
[ <any function, layer, virtual-function or namespace block> ]…
```

</Synopsis>

<Synopsis>

```c
// <name>.dsf — Dream Shader Function
[ import "<header>.dsh" ; ]…
[ { ShaderFunction | ShaderLayer | ShaderLayerBlend }( Name = "…" [, Root = "…"] ) { … } ]…
[ { VirtualFunction | Namespace | Function | GraphFunction } … ]…
```

</Synopsis>

<Synopsis>

```c
// <name>.dsh — Dream Shader Header
[ import "<header>.dsh" ; ]…
[ { VirtualFunction | Namespace | Function | GraphFunction } … ]…     // and 2.0 declarations, side by side
```

</Synopsis>

## What each kind may contain

| Top-level block | `.dsm` | `.dsf` | `.dsh` |
| :-- | :-: | :-: | :-: |
| `Shader` | one | no — `DSH2259` <Since v="2.1.1" /> | no |
| `ShaderFunction` | yes | yes | no |
| `ShaderLayer` | yes | yes | no |
| `ShaderLayerBlend` | yes | yes | no |
| `MaterialLayer` *(deprecated)* | yes | yes | no |
| `MaterialLayerBlend` *(deprecated)* | yes | yes | no |
| `VirtualFunction` | yes | yes | yes |
| `Namespace` | yes | yes | yes |
| `Function` | yes | yes | yes |
| `GraphFunction` | yes | yes | yes |
| `import` of a `.dsh` | yes | yes | yes |
| 2.0 declarations (`uniform`, `export`, `#pragma`, …) | no | no | yes |

A `.dsm` builds its `Shader` and every `ShaderFunction` or layer block beside it, each into its own
asset, as 1.x did; the material may call such a function by name, and the function's asset is built
first <Since v="2.1.1" /> (2.0.0 – 2.1.0 refused the pair with `DSH6201`). A `.dss` makes a material
*or* function assets, not both, so [`dsc migrate`](/en/docs/language-v2/migrate) wants each function
moved to a `.dsf` of its own first. See [Top-level Blocks](/en/docs/language/blocks) for what each
block declares.

## How the restriction is enforced

By the parser, one declaration at a time, and by the binder over the declarations of
one file <Since v="2.0.0" />.

| Rule | Checked by | Code |
| :-- | :-- | :-- |
| a `.dsh` holds no asset block (`Shader`, `ShaderFunction`, `ShaderLayer`, `ShaderLayerBlend` or an old spelling of a layer) | the legacy front end, at the block word | `DSH2249` |
| a `.dsm` / `.dsf` holds 1.x blocks only — a `uniform`, an `export`, a `#pragma` is 2.0 syntax | the legacy front end | `DSH2248` |
| a `.dss` holds 2.0 declarations only — a 1.x block word there | the 2.0 parser | `DSH3222` |
| one `Shader` block per file | the legacy front end | `DSH2250` |
| a `.dsf` holds no `Shader` block <Since v="2.1.1" /> | the legacy front end, at the block word | `DSH2259` |
| a `.dsm` / `.dsf` declares at least one block | the legacy front end | `DSH2254` |
| an `import` names a `.dsh` | the legacy front end | `DSH2252` |

A `.dsh` may hold 1.x blocks and 2.0 declarations side by side, so a project can migrate one file at a
time. A comment or a string that mentions `Shader(` is just a comment or a string.

<Callout type="info">

**Through 1.9.x** the rule was a case-insensitive **substring scan** of each file's text after its
`import` lines were removed: a `.dsh` was refused for containing `Shader(`, `ShaderFunction(`, … — in
a comment or a string too — while `Shader (` with a space slipped past. Nothing scans text any more:
the front end reads the block word, so a `.dsf` with a `Shader` block is `DSH2259` however it is
spaced (2.0.0 – 2.1.0 did not refuse it, and the file built a material like a `.dsm`).

</Callout>

## One file and the headers it imports

The unit of compilation is **one source file**. Each `.dsh` it imports is preprocessed and parsed on
its own, and its declarations are declared into the file <Since v="2.0.0" /> — nothing is pasted into
one text first.

- **At most one `Shader` block per file** (`DSH2250`). A header cannot hold a `Shader` at all
  (`DSH2249`), so an import never adds a second one. Through 1.9.x the whole import closure was inlined
  into one text, which made the limit closure-wide; it no longer is.
- **Only a `.dsh` can be imported** <Since v="2.0.0" />. An import of a `.dsf` or a `.dsm` is
  `DSH2252`: a material or function file is compiled on its own, and other files reach its assets
  through a [`VirtualFunction`](/en/docs/language/blocks#virtualfunction).
- Names span the file: a name a header declares that is declared again — in the file, or in a second
  header — is `DSH4210`. See [Imports and Namespaces](/en/docs/language/imports).

## What each kind generates

| Kind | Compiled as | Produces |
| :-- | :-- | :-- |
| `.dsm` | material entry point | the `UMaterial` (or ThinCustom instance) of its `Shader` block, plus every function and layer asset declared beside it |
| `.dsf` | asset entry point | the function assets it declares |
| `.dsh` | not an entry point | nothing — a header reaches the compiler only through the source that imports it; compiling one directly is `DSH8296` |

A `.dsm` with no `Shader` block is still compilable: it produces whatever function assets it does
declare. A compile builds what its own file declares, and never what a header it imports declares — a
header holds no asset block.

## Where files are found

Discovery runs over a list of **source roots**, not a single directory <Since v="1.6.0" />.

| Root | Directory | Writable | Contributed when |
| :-- | :-- | :-- | :-- |
| Project | *Source Directory*, `<Project>/DShader` by default | yes | always |
| one per plugin | `<Plugin>/DShader` | no | the plugin is enabled, the folder exists, and *Scan Plugin Source Directories* is on |

Each root owns a `<Root>/Packages` of its own. A root is the unit of import resolution: a specifier
resolves only inside the root that owns the importing file — see
[Imports and Namespaces](/en/docs/language/imports#source-roots). The editor only ever rewrites files
under the project root; plugin roots are discovered, parsed and compiled, never rewritten. A file
under a plugin root that writes no `Root=` generates into **that plugin's mount point** rather than
`/Game`; `Root="/"` opts back into `/Game`. See [Asset Paths](/en/docs/generation/asset-paths).

| Scan | Extensions | Excluded | Used for |
| :-- | :-- | :-- | :-- |
| All source files | `.dsm`, `.dsf`, `.dsh`; on the 2.0 line also `.dss`, `.dsi` and `.dsp` <Since v="2.1.0" /> | everything under any root's packages directory | dependency graph, workspace generation, editor file lists |
| Generatable files | `.dsm`, `.dsf`; on the 2.0 line also `.dss`, `.dsi`, `.dsp` — never `.dsh` | `.dsm` files under any root's packages directory | batch compile / generate-all |

<Callout type="info">

The two exclusions are not symmetric. The all-sources scan drops **every** file under a packages
directory; the generatable scan drops only package **`.dsm`** files. A `.dsf` shipped inside
`DShader/Packages` is therefore still picked up as a generatable file and will produce function
assets on a generate-all — and on the 2.0 line so is a `.dss`, a `.dsi` or a `.dsp` there.

</Callout>

| Directory | Default | Project setting |
| :-- | :-- | :-- |
| Source | `<Project>/DShader` | *Source Directory* |
| Packages | `<Source>/Packages` | derived from *Source Directory*; not separately configurable |
| Plugin source | `<Plugin>/DShader` | *Scan Plugin Source Directories* (on/off only; the path is fixed) |
| Generated shaders | `<Project>/Intermediate/DreamShader/GeneratedShaders` | *Generated Shader Directory* |

A configured relative path is resolved against the project directory. The project's source, packages
and generated-shader directories are created at module startup; a plugin's `DShader` folder is never
created, only discovered. See [Project Settings](/en/docs/settings/project) and
[Packages](/en/docs/tools/packages).

## Example

```text
<Project>/DShader/
├── Materials/
│   └── M_Water.dsm
├── Functions/
│   └── F_Tint.dsf
├── Shared/
│   └── Common.dsh
└── Packages/
    └── @typedreammoon/
        └── dream-noise/
            └── Library/
                └── Noise.dsh
```

```c
// DShader/Shared/Common.dsh — header: helpers only
Namespace(Name="Common")
{
    Function ApplyTint(in vec3 color, in vec3 tint, out vec3 result) {
        result = color * tint;
    }
}
```

```c
// DShader/Functions/F_Tint.dsf — function file: declares ShaderFunction blocks
import "Shared/Common.dsh";

ShaderFunction(Name="Functions/F_Tint")
{
    Inputs = {
        vec3 InColor;
        opt float Strength = 1.0;
    }

    Outputs = {
        vec3 OutColor;
    }

    Graph = {
        OutColor = Common::ApplyTint(InColor, vec3(1.0, 0.9, 0.8)) * Strength;
    }
}
```

```c
// DShader/Materials/M_Water.dsm — material file: one Shader block
import "Shared/Common.dsh";

Shader(Name="Materials/M_Water")
{
    Outputs = {
        vec3 Color;
        Base.EmissiveColor = Color;
    }

    Graph = {
        Color = Common::ApplyTint(vec3(0.1, 0.3, 0.6), vec3(1.0, 0.9, 0.8));
    }
}
```

Each source builds its own asset; the header builds nothing and is read by both:

```text
M_Water.dsm   ->  /Game/Materials/M_Water        UMaterial
F_Tint.dsf    ->  /Game/Functions/F_Tint         UMaterialFunction
Common.dsh    ->  (nothing)
```

## Notes

- A `.dsh` is the natural home for `VirtualFunction` declarations. The editor's *Create Virtual
  Function* action writes one under `DShader/VirtualFunctions`.
- The extension also decides the default extension of an unsuffixed import specifier: with no
  extension, `.dsh` is appended.
- A `.dsm` or `.dsf` must declare at least one block (`DSH2254`). An empty `Namespace` counts, and a
  `.dsh` may hold nothing but imports <Since v="2.0.0" />.
